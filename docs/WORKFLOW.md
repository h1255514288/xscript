# 新功能开发流程与协作规范

适用方式：你负责需求、优先级和业务验收，我负责调研、方案、实现、测试、文档与交付。适用于个人维护的 XScript 复刻；多人加入后仍沿用同一流程。

本文规定协作与交付方式；安装和命令见 [开发指南](DEVELOPMENT.md)，模块边界见 [扩展规范](EXTENDING.md)，当前建议排期见 [迭代计划](ITERATION_PLAN.md)。

## 1. 你怎样发起一个功能

直接用自然语言描述即可，不需要先写技术方案。下面五行可以直接复制给我；不知道的项可以留空：

```text
我要实现：
使用场景 / 当前遇到的问题：
希望在哪里使用：手机 / Web IDE / 桌面端 / 控制台 / 编辑器 / 不确定
怎样算完成：
限制与优先级：例如兼容现有脚本、只做单设备、优先于某需求
```

我先检查现有功能、源码、测试和上游变化，再判断是配置使用、缺陷修复、脚本开发还是平台扩展。已有能力能够满足时，先给出可用方案，避免重复实现。

需求明确后我按授权范围连续推进，常规目录选择、命名、实现细节和修复不反复找你确认。只有影响业务含义、成本、数据、兼容性或发布范围的关键选择无法推断时，才集中提出少量问题。已经明确的决定会写入功能记录，后面复用。

## 2. 分工与权限

| 事项 | 你负责 | 我负责 |
| --- | --- | --- |
| 需求 | 说明问题、目标和先后顺序 | 核对现状、补齐边界、拆分验收场景 |
| 方案 | 决定有明显取舍的业务规则 | 选择技术实现、定位影响模块、说明兼容和成本 |
| 开发 | 提供确实需要的设备或业务环境 | 分支、代码、必要测试、文档、排错 |
| 验收 | 按交付步骤体验，反馈通过或问题 | 提供可运行结果、演示步骤和证据，修复偏差 |
| 发布 | 决定面向谁、何时发布及接受的限制 | 在已授权范围内准备或执行发布、核验和回退 |

提交、推送、PR、合并和对外发布遵循本次任务的授权范围；已经授权的动作无需再确认。完成开发或合并代码，不自动等于已授权对外发布、升级生产环境或改变签名身份。需要你决定时，先准备好具体可审阅的结果、验证记录和影响说明。

无需强制创建 GitHub Issue：没有明确要求创建 Issue 时，在仓库内记录需求即可；获得创建 Issue 的指示后，再使用需求模板。不要为了走流程自动发布外部消息。

## 3. 状态流转

```mermaid
flowchart LR
    A["待梳理：描述问题"] --> B["可开发：范围与验收明确"]
    B --> C["开发中：实现与测试"]
    C --> D["待验收：交付可运行结果"]
    D -->|"不符合约定"| C
    D -->|"验收通过"| E["待发布：合并与发版准备"]
    E --> F["已发布：验证交付产物"]
```

| 状态 | 进入下一步的条件 | 留下什么 |
| --- | --- | --- |
| 待梳理 | 已核对已有能力；目的、入口和主要限制明确 | 一段需求说明 |
| 可开发 | 本期范围、暂不实现项、验收和验证环境已明确；关键决策已解决 | 功能记录、任务拆分、测试范围 |
| 开发中 | 实现完成、相关检查通过、必要手工/设备验证完成或明确受阻 | 代码、测试、文档、验证结果 |
| 待验收 | 你已按约定场景验收，反馈问题已处理；版本与证据对应 | 验收结果、遗留限制 |
| 待发布 | 目标提交的 CI 通过，版本、产物、兼容和回退方案齐备，发布范围已授权 | 发布记录、更新说明 |
| 已发布 | 正确产物可获取、目标环境冒烟通过、版本与签名符合预期 | Release/部署记录、验证时间与结果 |

受阻时保留原状态，补充阻塞原因、缺少条件和下一步；不把失败或跳过写成通过。验收中出现的新想法另排需求；与已约定行为不符的算本功能缺陷。

仅本机使用、无需发版的任务，以“已交付、验收通过、无需发布”结束，不虚构 Release。发布后出现问题进入关联修复任务，保留原来的版本记录。

## 4. 记录多少，按复杂度决定

| 类型 | 判断标准 | 最少记录 |
| --- | --- | --- |
| 小改动 | 文案、样式、文档，或局部修复；不变更公共契约和数据结构 | 任务/PR 中的目的、改动和验证结果 |
| 标准功能 | 新增用户行为，涉及一个或多个现有模块 | 一份 [功能说明](templates/FEATURE.md)、可验收的实现、[交付记录](templates/DELIVERY.md) |
| 复杂变更 | 接口不兼容、数据库迁移、签名/更新渠道变更，或有实际副作用的设备批量操作 | 标准功能记录，加方案取舍、兼容矩阵、恢复步骤和分阶段验证 |

功能说明保存为 `docs/features/FEATURE-001-主题.md`，编号按已有记录顺延；已有 Issue 时可在文件名中使用对应编号。复制模板后删掉不适用项，不要求每次重复填写整份清单。

需求范围和验收以功能说明为准；PR 放实现差异和 CI 证据；需要版本化的交付记录可以保存为 `docs/features/FEATURE-001-delivery.md`。不要在多处维护互相矛盾的功能状态。

## 5. 先判断功能属于哪一层

| 需求 | 默认落点 | 什么时候才扩展平台 |
| --- | --- | --- |
| 只让一个 App 完成某段自动化操作 | 设备工程或可复用的 `examples/` 示例 | 现有 API 明确缺少通用能力时 |
| 为多个脚本增加通用操作或识别能力 | `android/python-runtime/`；必要时连接 Android 原生桥接 | 需要设备能力、性能或权限支持时 |
| 增加按钮、表单、调试或编辑体验 | 对应的 Web IDE、桌面端、控制台或编辑器模块 | 客户端确实需要新协议时 |
| 增加任务、设备管理、授权或统计 | `backend/` 与相关客户端 | 需要新数据结构或设备指令时 |
| 增加供 AI 使用的工具 | `ide/mcp-server/` 复用现有设备客户端 | 设备本身没有相应接口时 |

新增功能按需修改相关层，不要求每个功能都修改 Android、后台、桌面端和 MCP。公共能力放在已有领域模块，UI 负责交互；不同客户端共用契约与业务规则，避免各写一套。

## 6. 标准开发步骤

### 6.1 调研和设计

先给出一份简短方案：现状与依据、用户将看到的变化、涉及模块、验收方式、关键限制。跨模块或复杂变更另说明接口、数据、升级与回退。没有必要时，不引入通用插件框架、事件总线、新服务或新的数据库。

将任务拆成可运行、可验收的小增量。一个 PR 对应一个明确目的；复杂功能可以先实现核心链路，再增加交互和边界处理，但只有约定范围全部完成才交付验收。

### 6.2 分支和提交

使用 `main` 加短期分支；现阶段不再增加长期 `develop` 分支。`main` 保持可构建，每次新工作先确认工作区和远端状态，不覆盖未提交的其他改动。

```bash
git switch main
git pull --ff-only origin main
git switch -c feat/feature-001-short-name
```

修复使用 `fix/…`，文档使用 `docs/…`，上游同步使用 `chore/sync-upstream-日期`。一个分支聚焦一个主题；多个任务同时做时使用独立工作目录，不互相切换正在使用的分支。

提交使用 `feat(模块): …`、`fix(模块): …`、`docs: …`、`test(模块): …` 等格式。不在功能 PR 中顺带升级无关依赖、整体格式化或重命名大量文件。

独立新功能一般采用 squash 合并，保留一个清晰的功能提交；上游同步采用保留历史的 merge，便于后续继续同步。不要强推共享 `main`，不要用重置主分支的方式覆盖复刻后的改动。

### 6.3 实现与自查

先完成最短用户链路，再处理重要错误路径。沿用项目现有语言、结构和命名；不建立与现有规范冲突的新风格体系。修改前找清入口、状态和数据归属，修改后检查差异是否超出本功能。

对设备操作明确权限、超时、停止和断连行为；不能通过无限重试掩盖失败。对会产生实际副作用的操作，先判断重试是否可能重复执行。日志应能关联设备、工程或任务，并说明失败原因，不记录真实令牌、密码或私钥。

新增 UI 要覆盖正常、等待、空数据、错误和重复提交等实际会出现的状态；错误提示告诉用户可采取的下一步。耗时操作不得阻塞 UI；需要持续运行的任务应支持用户停止。

不直接修改生成的类型存根、API 目录或节点规格；修改源头后执行 [扩展规范](EXTENDING.md) 中的生成器。

### 6.4 验证

先运行受影响范围的检查，发生新修改、失败或存在未解决问题时再补充验证。文档、样式和可逆的小改动不机械增加测试；行为变更用能验证实际结果的测试，修复缺陷尽量先复现。

| 改动类型 | 验证要求 |
| --- | --- |
| 文档/开发入口 | `python scripts/dev.py check repo`；检查新增文件是否纳入检查范围 |
| 后台/MCP | `python scripts/dev.py check python`；涉及数据库时看 PostgreSQL CI |
| 管理控制台 | `python scripts/dev.py check console`；用户路径的手工或浏览器验证 |
| VS Code 扩展 | `python scripts/dev.py check extension`；命令激活、调试 UI 等宿主行为需实际编辑器验证 |
| Web IDE | `python scripts/dev.py check webide`；涉及 UI 时配置浏览器，不能只看跳过浏览器的结果 |
| 设备 Python / Android | 对应运行时/JVM 检查、APK 构建，以及受影响能力的设备验证 |
| 桌面端 | 前端与 Python/Qt 测试，实际窗口或打包产物冒烟 |
| 数据/签名/更新机制 | 旧版本兼容、迁移或升级、失败恢复；在独立测试环境执行 |

Android、Qt 和设备命令见 [开发指南](DEVELOPMENT.md)，`dev.py` 没有对应目标时不能编造命令。CI 能证明它覆盖的自动检查通过，不能代替真机权限、ROM 行为和用户业务验收。

设备证据记录型号、Android 版本、运行模式、连接方式、App/脚本版本、操作与结果；模拟器结果单独标注。涉及截图/OCR时记录分辨率、方向、识别引擎和样例；性能改动在同一环境记录基线和修改后的测量值。

### 6.5 交付和验收

我每次提供：做了什么、使用入口、需要的前置条件、3～8 步可照着操作的验收步骤、预期结果、测试证据、已知限制，以及代码/可安装产物的位置。没有构建出的安装包，不写成“可下载安装”。

你只需反馈“通过”或说明哪一步与预期不同。反馈格式建议为“第几步、预期、实际、设备/环境”；技术原因由我分析。对于已有授权的修复，我继续处理，不要求重新提交整份需求。

代码审查由我完成：检查范围、接口兼容、边界条件、错误处理、资源释放、测试、日志和文档。业务验收由你完成；单人仓库不要求你为了形式上的审批去逐行审代码。

## 7. 新接口、数据与依赖规则

**接口：** 设备 HTTP 变化同步 `protocol/openapi.yaml`、设备实现、受影响客户端和 mock。后台 API 以现有 FastAPI 路由及模型为准，不把后台接口误写进设备契约。先写清输入、输出、错误、权限和超时；旧客户端/旧脚本遇到新增字段或缺少能力时要有明确行为。

**兼容：** 默认保持现有 `xscript.*` 和 `ascript.*` 的调用方式；无法兼容时列出受影响版本、迁移方法和替代方案。不能因为复刻就立即更改应用 ID、包名或签名。

**数据库：** 已发布表结构的变更通过 `backend/xscript_server/migrate.py` 增加迁移步骤；只改模型不等于旧库会升级。新增步骤兼容 SQLite/PostgreSQL，并验证新库、旧库升级、重复启动和失败场景。数据删除与不可逆转换必须在实施前明确范围及恢复策略。

**依赖：** 优先复用现有依赖；新增依赖说明用途、体积、许可证和平台支持。设备 Python 包还需验证 Chaquopy/Android ABI 支持；电脑上安装成功不代表手机可用。升级放在独立改动，保留 npm 锁文件与 Python 已声明的版本策略。

**配置：** 用户配置、业务数据与代码分开。仅在确有分阶段启用需求时加入小范围功能开关，并记录默认值、关闭后行为和后续清理时机；当前不假定存在全局功能开关系统。

## 8. 合并与 CI 规则

推荐通过 PR 合并到 `main`，PR 中关联需求和交付记录。合并前检查目标提交的 CI、冲突、遗留问题和验收状态；不要使用旧提交的通过记录替代当前提交。

当前已经有完整 [ci.yml](../.github/workflows/ci.yml) 和 [dev-tools.yml](../.github/workflows/dev-tools.yml)。建议之后启用以下仓库规则，**本方案没有自动更改 GitHub 设置**：

- `main` 通过 PR 更新；禁用强推和删除。
- 设置必需检查：`ci ok`、`portable checks (ubuntu-24.04)`、`portable checks (windows-latest)`、`Windows backend, MCP and editor checks`。启用时从实际检查列表选择，名称以后修改要同步规则。
- 要求讨论已解决。当前是单人维护，不强制“另一个账号批准”，避免自己无法完成审查；多人加入后再启用独立代码审查。

`ci ok` 汇总按路径选择的作业，适合作为完整 CI 的合并条件；不要把会被正常跳过的 Android 等单独作业一概设成必需检查。若某工作流以后增加 PR 路径过滤，应先确认必需检查不会永远处于等待状态。

紧急修复也保留最小复现、对应测试、变更记录和可追踪的合并。CI 红灯先定位原因，不通过降低覆盖率、删除断言或反复重跑来冒充通过。

## 9. 发布与恢复

代码交付、合并 `main` 和对外发布是三个可分别记录的结果。按 [发布检查表](templates/RELEASE.md) 准备版本，技术命令以 [发布流程](发布.md) 为准。

发布继续采用已有 `X.Y.Z` / `vX.Y.Z` 规则；兼容修复通常升补丁版本，新增兼容功能通常升次版本，破坏性变化先确定迁移政策。App、运行时、存根、VS Code/PyCharm 插件与桌面端按现有脚本同步版本。`backend/` 和 MCP 等另有包版本声明，不假定发布脚本会更新所有包，独立发布这些包时另行核对。

当前发布脚本只接受三段数字版本；不要直接设计 `vX.Y.Z-beta.1` 标签并假定能触发构建。试用先使用对应提交的 CI 产物或现有草稿 Release；需要正式预发布版本规则时单独实现。

复刻首次独立发布前，先解决自己的签名证书、应用身份、版本序列、下载链接和更新源。当前脚本有上游证书默认值，桌面端更新源仍指向上游；复制仓库不意味着这些配置已经属于自己。自己的签名无法覆盖安装由上游签名的同包名 APK；需要明确并存或迁移方案，不以卸载用户数据作为默认升级步骤。

恢复区分三类：

| 变更 | 恢复策略 |
| --- | --- |
| 代码/UI | 对已合并变更创建 revert 或修复 PR，运行对应检查；不重置共享历史 |
| 数据库 | 确认旧代码是否支持新结构；保留故障现场和升级后的新增数据，再决定恢复备份或向前修复 |
| APK/客户端更新 | 通常通过更高 `versionCode` 的修复包恢复行为；不能假定能安装低版本 APK，也不能复用其他签名 |

记录停止继续分发的条件、上一可用产物、备份位置和验证方法。只保留“能回滚”一句话不算恢复方案。

## 10. 迭代节奏与上游维护

每轮聚焦一个主要需求和与其相关的修复，先完成再开始下一个。以出现可验收结果为节奏，不给未经调研的功能承诺固定完成天数。

需求优先级由你决定，建议顺序：阻塞使用/数据正确性问题 → 直接服务当前业务的功能 → 稳定性和效率 → 体验优化。技术改造要说明它解除的实际阻碍，不单独追求目录更“漂亮”。

每轮开始、独立发版前检查上游变化。同步单独开分支，按 [贡献指南](../CONTRIBUTING.md) 保留历史合并，解决冲突并验证复刻新增能力；不把上游同步混入正在验收的功能 PR。

每轮记录三项事实即可：需求是否达到验收、交付后出现哪些缺陷、验证/构建中哪些步骤耗时或不稳定。依据这些事实调整下一轮，不在没有使用数据时承诺设备规模、吞吐量或识别成功率。

## 11. 一个功能怎样实际走完

**设计示例，未排期也未实现：**“脚本运行失败后，希望看到失败截图和最后一段日志，方便排查。”开始前先检查现有崩溃上报、截图与日志能力，确认真正缺少的部分。

首版可以限定为：指定入口运行的单设备工程，失败时保存一份诊断结果；不默认扩大成跨设备云端存储、自动重跑或 AI 分析。截图权限不存在时仍保存原始错误与日志，说明截图失败原因，不能掩盖真正的脚本异常。

我负责定位运行结束/错误入口，确定数据保留位置和用户查看入口，补充相关契约与测试。你要决定的是“哪些失败要留证据、在哪里查看、保存多久”等业务规则；示例中的保留数量、大小或时间在开发前明确，不硬编码未讨论的产品承诺。

可用验收场景：正常执行不产生失败记录；主动停止按约定处理；脚本报错可看到原始异常和日志；有截图权限时能查看图；缺权限时有明确提示且日志可看；同一次失败不重复创建记录；达到保留上限按约定清理；旧工程仍可运行。测试和记录就围绕这些场景展开。
