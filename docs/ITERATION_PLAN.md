## 阶段 A：形成能稳定验收的环境

目标：你能在自己的目标环境里运行、观察并判断功能是否满足需求。

| 工作 | 产出与完成条件 |
| --- | --- |
| 确定主要开发入口 | 明确本轮主要使用手机、Web IDE、桌面端、控制台或编辑器中的哪一个 |
| 整理本机工具 | Node 满足控制台依赖范围；开发 Android 时准备 JDK/SDK/Python 3.10/ADB；记录可复现的启动方式 |
| 选择测试设备 | 使用一台指定手机或模拟器，记录版本、权限、运行模式与连接方式；不操作无关设备 |
| 跑通一条主链路 | 连接 → 新建/上传工程 → 运行 → 看日志 → 停止 → 修正错误后重跑，有实际记录 |
| 设置协作约束 | 根据需要启用 `main` 分支保护；使用短期分支和可追踪交付记录 |

先按需求准备必要组件，不必为了开发一个控制台功能先装齐所有 Android、Qt 和 PyCharm 工具。

## 阶段 B：完成第一个真实业务功能

你给出一个最常遇到的问题，我核对已有能力并按照 [功能模板](templates/FEATURE.md) 拆分。

选题原则：使用频繁、结果容易判断、能在一个小增量中交付。暂不优先做“全面重构”“支持所有设备”“完整插件市场”等边界不清的任务。

完成条件：主要用户路径可用；重要失败场景有处理；相关测试通过；我提供使用步骤和证据；你验收通过。用这次实践调整模板中不必要的负担。

## 阶段 C：积累可复用能力

后续功能仍从具体需求出发，出现真实重复时再提取公共模块：复用设备连接和协议客户端、统一任务状态与错误表达、补齐常用模板和节点、改善诊断信息。

每轮观察现有回归用例是否覆盖关键用户路径，补上实际出现的缺陷。涉及性能时先测当前数据，再提出目标；不要把“更快、更稳定”直接当作验收标准。

上游的 [路线图](路线图.md) 和 [功能对照](功能对照.md) 仅作为候选需求来源。里面已有很多已完成能力，规划前需要逐项核实，不照搬“阶段”标题当作待开发列表。

## 阶段 D：第一次独立发布

在需要把安装包交给你或其他使用者长期使用时启动，与具体功能开发分开跟踪。

1. 决定维持当前品牌/应用 ID，还是使用自己的名称和可并存的应用 ID；写明已有数据和安装来源的迁移办法。
2. 准备自己的签名证书与备份，配置仓库发布所需 Secret，调整证书校验和下载/更新地址。
3. 定义自己的版本序列并检查已存在的上游标签；不要覆盖历史标签，也不假定复刻仓库已有同名 Release。
4. 按现有脚本生成草稿 Release，核验安装包、签名、校验和、版本与对应提交。
5. 用目标设备/系统验证安装、升级、关键功能和恢复方式；验收并取得对应发布授权后对外开放。

完成标准：使用者能获取到本仓库的正确产物，安装或升级行为符合说明，出现问题时有可执行的恢复方案。CI 构建成功不是唯一的发布标准。

## 每轮工作安排

默认同时开发一个主要需求。每轮开始确定优先级和范围，中途新需求进入候选列表；验收缺陷在当前轮修复。紧急问题可打断当前工作，但先留下进度、未完成项和恢复入口。

每个阶段结束留下可操作结果：环境阶段是运行记录，功能阶段是可验收行为，复用阶段是有真实调用方的公共能力，发布阶段是经验证的产物。工作量估算在选定具体功能并完成调研后给出。
